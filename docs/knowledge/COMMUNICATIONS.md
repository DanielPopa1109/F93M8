# Communications

CBM APP uses an STM32F411RE with external MCP2515 SPI classic CAN; DMU APP uses an STM32F407VE with on-chip bxCAN1. Each application owns separate `BSW/Com/{Can,CanIf,CanTp,PduR,Com,CanNm,CanSM,ComM}` implementations. Both `CanIf` configurations route standard CAN ID `0x710`. The extended-address request bytes are `0x54` (CBM) and `0x56` (DMU); responses use `0xF0`, and gateway FlowControl uses `0x41`. CanTp supports SF/FF/CF/FC, 256-byte buffers, sequence and timeout checks, and 5 ms processing. CBM's FC parser now reads BS at byte 2 and STmin at byte 3. These paths have cross-compiled source evidence, not executed or bus-tested results.

ZGW's current classic `NM3` PDU is the one-byte standard ID `0x3FF` frame, with PN1 at byte 0 (`0xFF` while active). Both F93 receive paths accept DLC 1 or greater, notify their project-local Com/CanNm copies, expire remote activity after 1 s, and coordinate full/silent/no communication through ComM and CanSM. DMU's bxCAN filter accepts `0x3FF`; addressed diagnostics temporarily hold its CAN communication awake. Gateway NM3 production is not treated as an endpoint transmit requirement. Physical controller/transceiver state changes and bus-off recovery are not yet connected, and the new state machines are not bench verified.

Application frames and signal encoding remain in CBM `CanSpi.c` and DMU `CanH.c`; there is no configured `CAN -> CanIf -> Com -> Application` or reverse `Application -> Com -> CanIf -> CAN` path yet. The independent FBLs still use legacy diagnostic CAN IDs and are incompatible with ZGW's routed TP path.
