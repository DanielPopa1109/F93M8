# F93 diagnostics — current source view

Both APPs receive complete routed UDS requests through their own Can/CanIf/CanTp/PduR stacks and dispatch a configured subset from `BSW/Diag/Dcm/Dcm.c`. The common set is `10/11/14/19/22/28/85/3E/31/2A`; hooks in `Dcm_App.c` preserve CBM controls and DMU camera/cluster/mileage services. DEM owns configured ECU-specific events and serializes persistent status through queued NvM. ClearDTC reports success only after durable completion, and reset waits for physical positive-response confirmation.

The APP `28 01 03` path now preserves COM reception while disabling configured application transmission; return to default session or S3 expiry restores it. `19 04` exposes the existing six-byte DEM snapshot as configured record 1, DID `F1A0` (`eventId`, status at allocation, occurrence, little-endian 24-bit allocation/change counter). `19 01/02` now return no DTCs for a zero effective status mask, while `19 0A` still enumerates supported DTCs. This is metadata captured at first failure, not an environmental snapshot such as voltage or temperature. `2A` still returns immediate data without a periodic scheduler, and bit-7 positive-response suppression is only handled for TesterPresent. See [selected DCM SWS trace](../autosar/DCM_SWS_TRACEABILITY.md) for exact applicability and open behavior.

The independent FBLs use the same CAN ID with CBM EA `0x54` and DMU EA `0x56`. They implement bounded session/read/erase/download/transfer/verify/reset behavior and an interlocked SRAM updater. CBM alone retains coding/calibration parameter-block transactions. See [FBL diagnostic protocol](../bootloader/DIAGNOSTIC_PROTOCOL.md) and [current four-project review](../modernization/CURRENT_STATE_REVIEW_2026-10-24.md). Host execution and freestanding FBL links do not establish live ZGW/FCD, board or vehicle behavior.
