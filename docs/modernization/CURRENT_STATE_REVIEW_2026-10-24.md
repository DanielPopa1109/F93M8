# CBM and DMU APP/FBL current-state review — 2026-10-24

This is a source, host-test and cross-build assessment of the four independent F93 projects. It uses ZGW as an architectural and routed-diagnostic example, not as a standards authority. The intended scope is an AUTOSAR Classic-like laboratory BSW with direct application calls and no RTE, implementing the configured ECU features rather than every optional module or service. There is no percentage of conformance: mandatory applicability has not been exhaustively classified, and no bench or vehicle evidence was collected.

## FCD compatibility boundary

Current FCD source in `D:\GitHub_Repos\ZGW\Scripts\FCD\FCD.pyw` sends extended session, `28 01 03`, `85 02`, programming session, then for APP `31 01 00 01` erase, `34 00 44` with BE32 address/size, block-counter `36`, optional CRC-bearing `37`, and reset. Both F93 resident FBLs implement this shape for a single contiguous APP image at their linked origins, with CRC/footer validation and bounded routed ISO-TP. FCD currently defaults TransferExit CRC on, which the updater path requires. Host tests exercise the resident/updater contract, but there is no live FCD-to-ZGW-to-ECU trace.

FCD's FBL phase selects block 2 (`31 01 02 00 02`) and starts the SRAM updater (`31 01 01 55`). Both default F93 resident FBLs intentionally return NRC `22` at updater entry because `FBL_UPDATER_ACTIVATION_ALLOWED` is off pending independent physical recovery. Thus **FCD resident-FBL replacement is not operationally compatible today**. The controlled enabled images and candidate binaries pass software tests only. `fcd_settings.json` marks CBM/DMU nodes simulated and unselected, and the payload rows require address/package review before use. Arbitrary sparse or multi-segment APP HEX cannot be sent as independent erase/download transactions to these FBLs. FCD and ZGW are gap owners for target selection, package/address policy and routed live validation; F93 owns target handling and recovery proof.

## Protocol and BSW boundary

- **ISO-TP:** SF/FF/CF/FC, sequence checks, FC block size/STmin handling, timeouts and real lower-layer TX completion are implemented and host-executed for APP and FBL. The design is one fixed 256-byte diagnostic connection per image with static buffering, 5 ms scheduling and a 200-tick timeout. Standard PduR start/copy-buffer APIs, all ISO 15765-2 edge cases, sub-millisecond STmin timing and physical bus timing are not proved. See the [official CAN transport SWS](https://www.autosar.org/fileadmin/standards/R4.3.1/CP/AUTOSAR_SWS_CANTransportLayer.pdf) and [ISO 15765-2 scope](https://www.iso.org/standard/84211.html).
- **UDS in APP:** A configured service table dispatches `10/11/14/19/22/28/85/3E/31/2A`; DEM clear waits for NvM result and reset waits for physical positive-response completion. `19 04` now encodes the persisted six-byte metadata snapshot as record 1 with DID `F1A0`. This is not yet ECU environmental capture. `19 01/02` return an empty result for a zero effective status mask; `19 0A` still lists supported DTCs. `2A` currently returns application data synchronously and has no periodic scheduler, so it does not yet behave as ReadDataByPeriodicIdentifier. Only TesterPresent handles bit-7 positive-response suppression. Session/NRC variants, cancellation and multi-client behavior remain partial. See the [DCM trace](../autosar/DCM_SWS_TRACEABILITY.md).
- **UDS in FBL:** `10/11/22/28/31/34/36/37/3E/85` are bounded to each target's address ranges. Erase/verify/reset transitions use pending or positive responses with physical confirmation; APP transfer requires a contiguous image at the linked origin and commits a validity footer last. Arbitrary sparse HEX transactions, standard security access and a recoverable resident-FBL replacement are not implemented. The default resident-updater activation remains disabled.
- **AUTOSAR-like BSW:** COM signal/PDU configuration, NM follower, logical mode arbitration, DCM/DEM and a journaled NvM are connected to the actual applications. Complete AUTOSAR module SWS/ECUC applicability, standard APIs, reentrancy, timing and all optional variants have not been reviewed or proved. There is deliberately no RTE; this is a design choice, not a full Classic Platform compliance claim. DEM's R20-11 trace remains partial; other modules use the repository's R4.3.1 review baseline.

## Defects corrected in this review

1. In each APP, `28 01 03` used to disable the shared COM I-PDU group, which disabled receive as well as transmit. DCM now gates configured application transmit separately; receiving normal COM PDUs and diagnostic traffic continues. Returning to default session explicitly or through S3 restores transmit. This covers the configured FCD preamble, not all CommunicationControl modes or a full BswM mode interface.
2. DMU CanSM set a 200-tick bus-off recovery timer but ignored it in `MainFunction`. It now holds silent communication for the configured quiet period before the requested mode can resume. This is a logical transmission gate; physical bxCAN recovery still needs bench proof.
3. Both APPs incorrectly used DEM's zero-mask all-DTC filter for UDS `19 01/02`, returning all configured DTCs when the tester selected no supported status bits. DCM now emits an empty count/list in that case, retaining the DEM zero-mask behavior for `19 0A`.
4. Both APPs persisted a six-byte primary snapshot but rejected every `19 04` request. DCM now returns configured record 1 under DID `F1A0`, with the original bytes unchanged. Unsupported record numbers still receive NRC `31`; real ECU environmental data and broader freeze-frame configurations remain open.
5. Both `NvM_IsIdle` helpers previously returned true before initialization. They now require `NvM_Ready`, so an invalid or not-yet-initialized store cannot release CBM's postrun sleep gate or appear ready to DMU's persistence scheduler.

The host diagnostics suites assert receive while TX is disabled, blocked/restored application TX on `28` and default-session/S3 transitions, and 200-tick bus-off gating. The new `19 01/02/04` cases check empty masks, routed multi-frame snapshot encoding, and unsupported record rejection. The persistence suites assert that uninitialized NvM is not idle. All twelve suites passed in the final re-run.
